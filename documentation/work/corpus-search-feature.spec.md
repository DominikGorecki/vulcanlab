# Title: Corpus Search Feature

## Summary

* Add a new "Search" navigation item above "Cleanup" for searching the entire corpus (works)
* Support lexical search, dense (vector) search, or hybrid search with RRF fusion
* Provide configurable UI controls for search modes, RRF parameters, heading-only filtering, and result preview length
* Display search results with bibliographic metadata, title breadcrumbs, and line information
* Enable click-through to view the full sanitized markdown with highlighted passages scrolled into view
* Reuse retrieval infrastructure from RAG but keep searches ephemeral (no persistence)

## Problem / Context

* Users currently lack a direct way to search their entire corpus of works for specific content
* The Cleanup feature provides basic lexical search but is limited to chunk deletion workflows
* RAG retrieval is query-focused and persists results, but users need ad-hoc corpus exploration
* No existing interface combines lexical and dense search with adjustable fusion parameters
* Users need to quickly locate passages and navigate to source documents with context

## Goals

* Provide a unified search interface for exploring the corpus
* Support multiple search modes: lexical only, dense only, or hybrid (both with RRF)
* Allow users to configure RRF fusion parameters (k constant, top-k candidates, weights)
* Display rich metadata including bibliographic information and hierarchical breadcrumbs
* Enable seamless navigation from search results to full source documents with highlighting
* Build reusable document viewing infrastructure at `/search/result/[chunk_id]/[start_line]/[end_line]`

## Non-goals (Strict)

* Persisting search queries or results to the database
* Query expansion or semantic term enrichment
* Reranking beyond RRF fusion (no BGE reranker integration)
* Real-time search (debounced/autocomplete)
* Search history or saved searches
* Bulk operations on search results (export, batch delete, etc.)
* Integration with evaluation or experiment workflows

## Scope

### In scope

* New `/search` page in the frontend UI
* New nav item "Search" positioned above "Cleanup" in the navigation bar
* Backend API endpoints for lexical, dense, and hybrid search
* Python core module for search logic (`src/vulcanlab/search/`)
* UI controls for search mode selection, RRF parameters, heading-only filter, and result word limit
* Search result display with title breadcrumbs, bibliographic info, content preview, and metadata
* Click-through routing to `/search/result/[chunk_id]/[start_line]/[end_line]`
* Document viewer page displaying full sanitized markdown with passage highlighting and auto-scroll
* Pagination for search results (matching cleanup pattern)

### Out of scope

* Database schema changes (uses existing chunks, works, embeddings tables)
* Authentication or access control (relies on existing API setup)
* Advanced filters (date ranges, work type, author filtering)
* Search analytics or logging
* Export functionality for search results
* Mobile-optimized UI (desktop-first)

## Requirements (Functional)

* R1: The system MUST provide a search page accessible via `/search` in the UI
* R2: The navigation bar MUST include a "Search" item positioned directly above "Cleanup"
* R3: The search UI MUST allow users to select one or more search modes: lexical, dense, or both
* R4: When both search modes are selected, the system MUST perform RRF fusion on results
* R5: The search UI MUST provide controls for RRF parameters: k constant, dense top-k, lexical top-k, and optionally weights
* R6: The search UI MUST provide a "headings only" checkbox to filter results to H1-H5 chunks
* R7: The search UI MUST provide a slider or input to set maximum preview word count per result
* R8: Search results MUST display: title breadcrumb, bibliographic info (title, author, year), content preview, chunk metadata (level, lines, work_id, chunk_id)
* R9: Title breadcrumbs MUST be generated by traversing the chunk hierarchy upward to H1
* R10: Each search result MUST be clickable to navigate to `/search/result/[chunk_id]/[start_line]/[end_line]`
* R11: The document viewer page MUST display the full sanitized markdown for the chunk's work
* R12: The document viewer MUST highlight the passage corresponding to start_line and end_line
* R13: The document viewer MUST auto-scroll to the highlighted passage on page load
* R14: Search results MUST be paginated with prev/next controls (matching cleanup pattern)
* R15: Dense search MUST reuse the same embedding model and vectorization configuration as RAG
* R16: Lexical search MUST use PostgreSQL full-text search (ts_vector/ts_query)
* R17: RRF fusion MUST combine dense and lexical results using the reciprocal rank fusion algorithm
* R18: Search queries MUST NOT be persisted to the database
* R19: The backend API MUST return results with consistent structure including chunk_id, work metadata, content, scores, and rankings

## Requirements (Non-functional)

* Performance:
  * Dense search queries MUST complete within 3 seconds for datasets up to 100k chunks
  * Lexical search queries MUST complete within 1 second
  * Hybrid search (RRF) MUST complete within 4 seconds
  * Document viewer page load MUST complete within 2 seconds
* Reliability:
  * Search API MUST handle missing embeddings gracefully (skip chunks without embeddings in dense mode)
  * UI MUST display error messages for failed searches without crashing
  * Navigation to non-existent chunks MUST return a 404 page
* Security / Privacy:
  * Search queries MUST be validated and sanitized to prevent SQL injection
  * API endpoints MUST follow existing authentication/authorization patterns
* Observability:
  * Backend MUST log search parameters (mode, query, filters) at INFO level
  * Backend MUST log search execution times at DEBUG level
  * UI MUST display loading states during search execution

## Proposed Solution (High-level)

* **Frontend**: Add a new `/search` page in `vulcanlab_ui/src/app/search/page.tsx` using Client Components
* **Frontend**: Add a new `/search/result/[chunk_id]/[start_line]/[end_line]` dynamic route for document viewing
* **Frontend**: Update `nav-bar.tsx` to include the "Search" item above "Cleanup"
* **Backend API**: Create new router in `src/vulcanlab_api/routers/search.py` with endpoints:
  * `GET /api/v1/search/lexical` - Lexical-only search
  * `GET /api/v1/search/dense` - Dense-only search
  * `GET /api/v1/search/hybrid` - Hybrid search with RRF fusion
  * `GET /api/v1/chunks/{chunk_id}/markdown` - Retrieve sanitized markdown for a chunk's work
* **Backend Core**: Create new module `src/vulcanlab/search/` with:
  * `search_lexical.py` - Lexical search using ts_vector
  * `search_dense.py` - Dense search using pgvector similarity
  * `search_hybrid.py` - RRF fusion of lexical + dense results
  * `breadcrumb_builder.py` - Hierarchical breadcrumb generation by traversing parent chunks to H1
* **Data Flow**:
  1. User enters query and selects search mode/parameters in UI
  2. UI calls appropriate API endpoint with query string, filters, and RRF params
  3. API router validates inputs and calls core search module
  4. Core module executes database queries (lexical, dense, or both)
  5. If hybrid, core module applies RRF fusion with configurable k constant and weights
  6. Core module generates breadcrumbs by traversing chunk hierarchy
  7. Core module fetches work metadata (title, author, year) via JOIN
  8. API returns paginated results with scores, metadata, and preview content
  9. UI displays results; user clicks a result
  10. UI navigates to `/search/result/[chunk_id]/[start_line]/[end_line]`
  11. Document viewer fetches sanitized markdown via `GET /api/v1/chunks/{chunk_id}/markdown`
  12. Viewer highlights passage using line numbers and scrolls to start_line

## Interfaces / APIs / Contracts

* **GET /api/v1/search/lexical**
  * Query params: `q` (string, required), `page` (int, default 1), `page_size` (int, default 20), `headings_only` (bool, default false), `top_k` (int, default 20)
  * Response: `{ results: SearchResult[], pagination: PaginationInfo }`

* **GET /api/v1/search/dense**
  * Query params: `q` (string, required), `page` (int), `page_size` (int), `headings_only` (bool), `top_k` (int, default 20)
  * Response: `{ results: SearchResult[], pagination: PaginationInfo }`

* **GET /api/v1/search/hybrid**
  * Query params: `q` (string, required), `page` (int), `page_size` (int), `headings_only` (bool), `rrf_k` (int, default 60), `dense_top_k` (int, default 20), `lexical_top_k` (int, default 20), `dense_weight` (float, default 0.5), `lexical_weight` (float, default 0.5)
  * Response: `{ results: SearchResult[], pagination: PaginationInfo, rrf_stats: RRFStats }`

* **GET /api/v1/chunks/{chunk_id}/markdown**
  * Path param: `chunk_id` (int, required)
  * Response: `{ work_id: int, work_title: str, markdown_content: str, chunk_start_line: int, chunk_end_line: int }`

* **SearchResult** (shared response model):
  ```typescript
  {
    chunk_id: number
    work_id: number
    work_title: string
    work_authors: string | null
    work_year: number | null
    heading_breadcrumbs: string
    content_preview: string
    start_line: number
    end_line: number
    level: string
    score: number  // RRF score for hybrid, relevance score otherwise
    dense_rank?: number
    lexical_rank?: number
  }
  ```

* **PaginationInfo**:
  ```typescript
  {
    page: number
    page_size: number
    total_results: number
    has_next: boolean
    has_prev: boolean
  }
  ```

* **RRFStats**:
  ```typescript
  {
    dense_candidates: number
    lexical_candidates: number
    fused_count: number
    rrf_k: number
  }
  ```

## Data Model / Storage

* No new tables required
* Uses existing tables:
  * `chunks` - For chunk content, hierarchy (parent_id), and metadata
  * `works` - For bibliographic information (title, authors, year)
  * `embeddings` - For dense vector search (pgvector similarity)
* Query pattern for breadcrumb generation:
  * Recursive CTE or iterative query traversing `chunks.parent_id` up to root (level='H1' or parent_id IS NULL)
* Query pattern for dense search:
  * `SELECT ... FROM chunks JOIN embeddings ... ORDER BY embedding <=> query_vector LIMIT top_k`
* Query pattern for lexical search:
  * `SELECT ... FROM chunks WHERE to_tsvector(content) @@ to_tsquery(query) ORDER BY ts_rank(...) LIMIT top_k`

## UX / Workflows

* **Search Workflow**:
  1. User navigates to "Search" from nav bar
  2. User enters query text in search input
  3. User selects search mode via radio buttons or checkboxes: "Lexical", "Dense", "Both"
  4. If "Both" selected, user adjusts RRF parameters (k, top-k counts, weights) via collapsible settings panel
  5. User optionally enables "Headings only" checkbox
  6. User adjusts "Max preview words" slider (default 100, range 50-500)
  7. User clicks "Search" button
  8. UI displays loading spinner
  9. Results appear below with pagination controls
  10. User clicks on a result card
  11. Browser navigates to `/search/result/[chunk_id]/[start_line]/[end_line]`
  12. Document viewer loads, highlights passage, and scrolls to it

* **Document Viewer Workflow**:
  1. Page loads with chunk_id, start_line, end_line from URL params
  2. Fetches sanitized markdown via API
  3. Renders markdown with syntax highlighting
  4. Identifies lines matching start_line to end_line range
  5. Applies highlight styling (yellow background or border)
  6. Uses `scrollIntoView` or similar to auto-scroll to highlighted passage
  7. User can scroll up/down to see full document context
  8. User can click "Back to Search" to return to results

## Risks and Alternatives

* Risks:
  * Dense search performance may degrade with large datasets (>100k chunks) - mitigation: index embeddings with IVFFlat or HNSW
  * RRF fusion complexity may confuse users - mitigation: provide sensible defaults and collapsible advanced settings
  * Breadcrumb generation via recursive hierarchy traversal may be slow - mitigation: consider caching breadcrumbs in chunks table (out of scope for this spec)
  * Highlighting passages by line number may be fragile if sanitized markdown is re-generated - mitigation: document the assumption that markdown is stable
  * Reusing `/search/result/[chunk_id]/[start_line]/[end_line]` pattern elsewhere may cause route conflicts - mitigation: design generic document viewer component

* Alternatives considered:
  * **Alternative 1: Use Elasticsearch instead of PostgreSQL for search**
    * Pros: Better full-text search, faster for large datasets, faceted search support
    * Cons: Adds infrastructure complexity, requires separate service and sync logic
    * Decision: Stick with PostgreSQL for simplicity (aligns with patterns.md)
  * **Alternative 2: Persist searches to database like RAG queries**
    * Pros: Enables search history, analytics, repeat searches
    * Cons: Adds schema complexity, not required by user (ephemeral search is sufficient)
    * Decision: Keep searches ephemeral per user request
  * **Alternative 3: Include BGE reranking in search pipeline**
    * Pros: Improves result quality, aligns with RAG retrieval
    * Cons: Adds latency, requires GPU resources, increases complexity
    * Decision: Defer reranking to future iteration (user requested optional reranking, but out of scope for initial implementation)

## Implementation Notes (Non-binding)

* Consider reusing cleanup's search result card design as a starting point, but enhance with bibliographic metadata
* Breadcrumb generation could be optimized with a recursive CTE in PostgreSQL or a `WITH RECURSIVE` query
* The document viewer could be extracted as a reusable component for future features (e.g., chunk detail view, RAG context inspection)
* RRF fusion formula: `score = sum(1 / (k + rank_i))` where k is the constant and rank_i is the rank in each result set
* RRF weights MUST be normalized to sum to 1.0 before applying to scores
* For dense search, reuse `vulcanlab.retrieval.retrieve` logic for embedding generation (query vectorization)
* Consider adding a "Copy to clipboard" button for search results (defer to future iteration)
* Frontend state management: Use `useState` for search parameters, `useCallback` for fetch functions to avoid infinite loops
* Pagination offset calculation: `offset = (page - 1) * page_size`
* Highlighting implementation: Parse markdown into lines, wrap target lines in `<mark>` or apply CSS class
* Document viewer MUST render formatted markdown using a markdown renderer (e.g., `react-markdown`)
* Max preview word limit applies per-chunk (not total across page)
* Orphaned chunks with no parent MUST display "[No heading]" as breadcrumb
