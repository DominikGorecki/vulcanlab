# Title: Evaluation Automatic Mode with Multi-Provider LLM Support

## Summary

* Enable automatic evaluation workflow where answer generation and judging use different LLM providers
* Add toggle on experiment detail page to enable/disable automatic mode
* Store automatic mode configuration (enabled state, answer provider, judge provider) on Experiment model
* When automatic mode is enabled, the "Add Answers" button becomes "New Eval" which triggers a three-prompt workflow
* Create grouped prompt system where main prompt, answer_x prompt, and answer_y prompt are linked
* Execute automatic eval synchronously: generate answer_x, generate answer_y, then run judge evaluation
* Extend llm_factory to support explicit provider selection via new factory functions for backwards compatibility
* Always use FULL tier models for both answer generation and judge in automatic mode

## Problem / Context

* Currently, the eval system uses a single LLM provider configured globally in vulcanlab.config.json
* Users cannot easily compare answers generated by different providers (OpenAI vs Gemini)
* Manual workflow requires users to generate answers externally and paste them in
* There is no automated way to run comparative evaluations between two LLM providers
* The current llm_factory only supports one provider at a time based on global config
* Users want to test "GPT-4 vs Gemini" scenarios where one provider generates answers and the other judges

## Goals

* Enable experiments to run in "automatic mode" with provider-specific answer generation and judging
* Store automatic mode configuration persistently on the Experiment model
* Support both OpenAI and Gemini as answer generators and judges
* Provide UI toggle on experiment detail page to enable/disable automatic mode
* Implement grouped prompt workflow (main, answer_x, answer_y) linked by group_id
* Execute full automatic eval workflow synchronously in a single API call
* Maintain backwards compatibility with existing llm_factory usage
* Ensure automatic mode uses FULL tier models for quality

## Non-goals (Strict)

* Async/background task execution for automatic eval (future enhancement)
* Support for more than two providers (OpenAI and Gemini only)
* Provider selection at individual prompt level (only at experiment level)
* Manual answer submission in automatic mode (use manual mode instead)
* Automatic mode for anything other than FULL tier models
* Migration of existing experiments to automatic mode (manual opt-in only)

## Scope

### In scope

* Database schema changes: add auto_mode_enabled, auto_answer_provider, auto_judge_provider to experiments table
* Database schema changes: add prompt_group_id to experiment_prompts table
* Migration SQL file for schema changes
* Updates to init_db.py for fresh installs
* New factory functions in llm_factory.py that accept explicit provider parameter
* API endpoint modifications for experiment update (toggle automatic mode)
* API endpoint for "New Eval" workflow (create grouped prompts, generate answers, submit evaluation)
* UI toggle component on experiment detail page
* UI dialog for "New Eval" to collect answer_x and answer_y prompts
* UI button state change ("Add Answers" to "New Eval") based on automatic mode
* Core logic for orchestrating three-step automatic evaluation

### Out of scope

* Background/async task execution
* Provider selection UI during experiment creation (only on detail page)
* Batch automatic eval for multiple prompts
* Custom tier selection for automatic mode
* Automatic retry logic for failed LLM calls
* Streaming responses for automatic eval
* Cost tracking for multi-provider usage

## Requirements (Functional)

* R1: Experiment model must have three new fields: auto_mode_enabled (boolean), auto_answer_provider (string), auto_judge_provider (string)
* R2: ExperimentPrompt model must have prompt_group_id (nullable integer) to link main, answer_x, and answer_y prompts
* R3: When auto_mode_enabled is true and auto_answer_provider is set, auto_judge_provider must be the opposite provider
* R4: UI must display a toggle on /eval/[id] page to enable/disable automatic mode
* R4a: Before enabling automatic mode, system must validate that both OpenAI and Gemini API keys are present in .env
* R5: When enabling automatic mode, user must select answer provider (Gemini or OpenAI); judge is automatically set to opposite
* R6: When automatic mode is enabled, the "Add Answers" button on /eval/[id]/prompts/[promptId] must change to "New Eval"
* R7: "New Eval" button must open dialog to collect answer_x prompt and answer_y prompt text
* R8: Submitting "New Eval" dialog must create three ExperimentPrompt records with same prompt_group_id (unique within experiment)
* R9: After creating prompts, system must execute automatic eval: run answer_x prompt on answer provider, run answer_y prompt on answer provider, generate both answers, then run judge evaluation
* R9a: During automatic eval execution, UI must show progress indicator with current step (e.g., "Step 1/3: Generating answer X...")
* R10: All LLM calls in automatic mode must use FULL tier models
* R11: Automatic eval must execute synchronously (user waits for completion)
* R12: llm_factory must have new functions create_langchain_chat_for_provider and create_embeddings_for_provider that accept explicit provider parameter
* R13: Existing llm_factory functions must remain unchanged for backwards compatibility
* R14: When automatic mode is disabled, behavior must be identical to current manual workflow
* R15: Disabling automatic mode does not delete or invalidate existing grouped prompts; it only prevents creation of new automatic evals
* R16: prompt_group_id must be unique per experiment (not globally unique)

## Requirements (Non-functional)

* Performance:
  * Automatic eval with three LLM calls should complete within reasonable time (typically 30-90 seconds for FULL models)
  * UI must show loading/progress state during synchronous execution
* Reliability:
  * If any LLM call fails, entire automatic eval transaction should rollback (no partial state)
  * Clear error messages for LLM API failures
* Security / Privacy:
  * API keys for both OpenAI and Gemini must be read from .env file
  * No API keys exposed in responses or logs
* Observability:
  * Log which provider is used for each step of automatic eval
  * Log model names (FULL tier) used for answer generation and judging

## Proposed Solution (High-level)

* Add three columns to experiments table via migration and init_db update
* Add prompt_group_id column to experiment_prompts table
* Create new llm_factory functions that accept provider parameter and override global config
* Add PATCH endpoint to toggle automatic mode on experiment
* Add POST endpoint for "New Eval" workflow that orchestrates three prompts and automatic eval
* Add toggle UI component on experiment detail page with provider selection
* Add dialog component for "New Eval" with two text areas for answer_x and answer_y prompts
* Conditional rendering of "Add Answers" vs "New Eval" button based on experiment.auto_mode_enabled
* Core logic function to execute automatic eval: generate_and_evaluate_auto(main_prompt, answer_x_prompt, answer_y_prompt, answer_provider, judge_provider)

## Interfaces / APIs / Contracts

* PATCH /api/v1/eval/experiments/{experiment_id}
  * Request body: { auto_mode_enabled: boolean, auto_answer_provider?: "openai" | "gemini" }
  * Response: Updated ExperimentDetail
  * Sets auto_judge_provider automatically to opposite of auto_answer_provider
* POST /api/v1/eval/experiments/{experiment_id}/prompts/auto-eval
  * Request body: { main_prompt_id: number, answer_x_prompt_text: string, answer_y_prompt_text: string }
  * Response: { evaluation_id: number, answer_id: number, prompt_group_id: number }
  * Creates three prompts, generates answers, submits evaluation
* ExperimentDetail schema extension:
  * auto_mode_enabled: boolean
  * auto_answer_provider: string | null
  * auto_judge_provider: string | null
* ExperimentPrompt schema extension:
  * prompt_group_id: number | null

## Data Model / Storage

* experiments table additions:
  * auto_mode_enabled BOOLEAN NOT NULL DEFAULT FALSE
  * auto_answer_provider VARCHAR(50) NULL
  * auto_judge_provider VARCHAR(50) NULL
  * Constraint: if auto_mode_enabled is true, both provider fields must be non-null
* experiment_prompts table additions:
  * prompt_group_id INTEGER NULL (unique within experiment_id, not globally unique)
  * Index on (experiment_id, prompt_group_id) for efficient grouped prompt queries
* Migration file: migrations/016_add_auto_eval_mode.sql
* init_db.py updates: create columns and constraints during table creation

## UX / Workflows

* Workflow 1: Enable automatic mode
  * User navigates to /eval/[id]
  * User clicks toggle "Enable Automatic Mode"
  * System validates both OpenAI and Gemini API keys are present in .env
  * If validation fails, show error: "Both OpenAI and Gemini API keys required. Please check .env configuration."
  * If validation passes, dialog appears: "Select answer generation provider: [Gemini] [OpenAI]"
  * User selects provider
  * System saves experiment with auto_mode_enabled=true, auto_answer_provider=selected, auto_judge_provider=opposite
  * Page refreshes to show automatic mode active
* Workflow 2: Run automatic eval
  * User navigates to /eval/[id]/prompts/[promptId] (automatic mode is enabled)
  * User sees "New Eval" button instead of "Add Answers"
  * User clicks "New Eval"
  * Dialog appears with three sections: "Main Prompt" (read-only, pre-filled), "Answer X Prompt" (textarea), "Answer Y Prompt" (textarea)
  * User enters prompts for answer_x and answer_y
  * User clicks "Submit"
  * Loading state shows "Step 1/3: Generating answer X..."
  * System creates three prompts with same prompt_group_id (max(prompt_group_id) + 1 for this experiment)
  * System runs answer_x prompt on answer provider (FULL tier) to get answer_x
  * Loading state updates: "Step 2/3: Generating answer Y..."
  * System runs answer_y prompt on answer provider (FULL tier) to get answer_y
  * System creates ExperimentAnswer with answer_x and answer_y
  * Loading state updates: "Step 3/3: Running judge evaluation..."
  * System generates eval prompt and runs on judge provider (FULL tier)
  * System creates ExperimentEvaluation
  * Success toast: "Automatic evaluation completed"
  * Page refreshes to show new evaluation
* Workflow 3: Disable automatic mode
  * User navigates to /eval/[id]
  * User clicks toggle "Disable Automatic Mode"
  * Confirmation dialog: "Disable automatic mode? Manual answer submission will be available. Existing automatic evaluations will remain unchanged."
  * User confirms
  * System saves experiment with auto_mode_enabled=false
  * Page refreshes, "Add Answers" button returns on prompt pages
  * Existing grouped prompts and evaluations remain visible and unchanged

## Risks and Alternatives

* Risks:
  * Synchronous execution may timeout for slow LLM responses (mitigation: implement timeout handling and clear error messages)
  * Users may be confused by automatic vs manual mode distinction (mitigation: clear UI labels and help text)
  * Cost implications of always using FULL tier models (mitigation: document this clearly, users opt-in knowingly)
* Alternatives considered:
  * Background task execution: Adds complexity with celery/redis, deferred to future
  * Provider selection per prompt: Too granular, experiment-level is sufficient
  * Support LIGHT tier in automatic mode: Rejected for quality reasons

## Implementation Notes (Non-binding)

* Use transaction rollback if any step of automatic eval fails (all-or-nothing)
* The three prompts (main, answer_x, answer_y) should be created with sequential display order
* prompt_group_id is auto-generated as max(prompt_group_id) + 1 for the experiment (scoped to experiment_id)
* UI loading state during automatic eval shows step progress ("Step 1/3", "Step 2/3", "Step 3/3")
* API key validation should check both LLMSettings().openai_api_key and LLMSettings().google_api_key are non-null
* Consider adding a "View grouped prompts" feature in future to see related prompts together
* The automatic eval endpoint should log timestamps for each LLM call for performance monitoring
* Provider strings should use LLMProvider enum values ("openai", "gemini")
* Disabling automatic mode only changes auto_mode_enabled flag; does not cascade delete grouped prompts
